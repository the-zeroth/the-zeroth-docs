单个 Agent 的哲学是上下文的哲学。我们在[上下文与冥想](../single-agent/context)一节提到过：

> 要评判一个 Agent 上下文的好坏，根本在于约束（**我是谁？**）、信息（**从哪里来？**）、任务（**到哪里去？**）这三点是否完整、明确、清晰；与这三点无关的冗余上下文应尽可能剔除。

复杂的任务会让这三点同时难以保持。一个 Agent 既当实现者又当验收者，“我是谁”就不再清楚；它为一个子任务读进来的东西，会一直留在做下一个子任务的上下文里。把活分给几个角色清晰、只拿到自己那部分信息的 Agent，为的就是让每个 Agent 的上下文保持洁净。

## 多一个 Agent，不一定更好

但 Agent 不是越多越好。从实际运行里，我们得出了这样几条：

- **多开几份同样的 Agent，只会错在同一处。** 同一个模型拿着同样的输入，各做一份再挑一份，往往不比一个做得好，还贵上好几倍。一个节点值不值得加，要看它的错和已有节点的错有多不相关。
- **有用的节点，看的东西不一样。** 只看需求原文的验收检查员、只看代码仓库的惯例检查员、只看报告和数据的症状检查员，发现的是负责人看不到的问题。换一个模型，也是让错误不相关的办法。
- **核验者不从被核验的东西里拿答案。** 读了实现的检查员，会继承实现的错。给核验者的是需求、数据和接口，不给实现。
- **信息要在拍板之前到。** 关键的写法往往在头几步就定了，晚到的意见很少推翻已经做好的东西。所以专家节点要在开工时就和负责人并行启动，而不是排在它后面。
- **负责人的路径就是成本。** 负责人的回合占了大部分模型时间，它的路径上每多一跳，就要多走几轮。一个节点的收益要大过它增加的回合，才值得加。
- **说明要在用到时出现。** 一直挂在上下文里的规则，用不上时也在起作用，会把别的活带偏。规则应该放进它所管的那份产物的交回说明里，或者放进做那件事时才打开的技能。

所以设计一支团队时，默认是**一个工具齐全的负责人**：大多数活它自己做；需要时，它在开工时就并行启动几个看不同东西的检查员，或者开一个 TaskBoard，把能独立完成的部分分给几对 worker 和 reviewer。出厂的软件团队就是这样搭的。节点数是结果，不是目标。

## 在 The One 里

主助手把一个事项的活交给一个**工作组**：照一份工作组模板组建，每个角色有自己的指令，移交时只传过去发出方选择交出的内容。见[工作组](../../the-one-app/working-groups)和[工作组模板](../../the-one-app/capabilities/working-group-templates)。

一套被验证有效的协作结构，可以连同每个成员的提示词、技能和工具，被完整写成一份可复用的模板，这就是 [A-Genetic Engineering（Agent 基因工程）](../a-genetic-engineering)；Agent 在运行时按需创建、克隆、连接其他 Agent，让团队边做边长，这就是 [Prolifera Engineering（增殖式工程）](../prolifera-engineering)。
