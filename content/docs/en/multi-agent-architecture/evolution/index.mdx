A single Agent is a context problem. As [Context and meditation](../single-agent/context) puts it:

> The quality of an Agent's context comes down to whether its constraints (**who am I?**), information (**where do I come from?**) and task (**where am I going?**) are complete, explicit and clear, and whether context that serves none of them has been left out.

Complex work makes all three hard to keep at once. An Agent that both builds the work and checks it no longer knows clearly who it is; what it read for one subtask stays in its context while it does the next. Splitting the work among Agents with clear roles, each given only its own part of the information, is how each Agent's context stays clean.

## Another Agent is not always better

But more Agents are not always better. From real runs, we have learned these things:

- **Copies of the same Agent go wrong in the same place.** The same model with the same input, each copy making its own version and one picked at the end, often does no better than a single Agent and costs several times as much. Whether a node is worth adding depends on how little its mistakes have in common with those of the nodes already there.
- **Useful nodes look at different things.** An acceptance checker that reads only the request, a convention checker that reads only the repository, a symptom checker that reads only the report and the data: each finds problems the lead cannot see. Using a different model is another way to make mistakes independent.
- **A checker does not take its answers from what it checks.** A checker that has read the implementation inherits its mistakes. Give checkers the request, the data and the interfaces, not the implementation.
- **Information must arrive before the decision.** The key choices are often made in the first few steps, and late feedback rarely overturns work already done. So specialist nodes start alongside the lead when the work starts, not after it.
- **The lead's path is the cost.** The lead's turns take most of the model time, and every extra hop on its path costs it more turns. A node is worth adding only when what it brings outweighs the turns it adds.
- **Instructions should appear where they are used.** A rule that sits in the context all the time works even when it does not apply, and pulls other work off course. Put a rule in the handoff instructions of the output it governs, or in a Skill the Agent opens only when it does that work.

So when a team is designed, the default is **one well-equipped lead**: it does most of the work itself; when it helps, it starts a few checkers that look at different things alongside itself from the start, or opens a TaskBoard and gives the parts that stand on their own to pairs of workers and reviewers. The shipped software team is built this way. The number of nodes is an outcome, not a goal.

## In The One

The main assistant gives a matter's work to a **working group**, assembled from a working-group template: each role has its own instructions, and a handoff passes only what the sender chooses to hand over. See [Working groups](../../the-one-app/working-groups) and [Working-group templates](../../the-one-app/capabilities/working-group-templates).

A collaboration structure that has proven itself can be written down in full as a reusable template, with every member's prompts, Skills and tools: that is [A-Genetic Engineering](../a-genetic-engineering). Agents creating, cloning and connecting other Agents at runtime as the work needs them, so the team grows as it goes: that is [Prolifera Engineering](../prolifera-engineering).
