A **working-group template** says how one kind of work is shared out: which roles take part, who may hand work to whom, and how the result gets checked. When the main assistant gives a matter's work away, it starts a new run of a template, and that run is a **working group**. See [Working groups](../working-groups).

Templates are Graphs. The editor, its tab (**Graph**) and the runs under **Settings › All runs** still use that word. You find them in **Capabilities › Working-group templates**.

## How a template becomes a working group

- The main assistant sees every template in the Space with the first 800 characters of its description, and picks one for each piece of work. Software work in a project goes to `polished_software_dev`, a studio's kind of work to that studio, and ordinary multi-step work to `chat`.
- Each assignment starts a new run of the template, in the folder the work belongs to. Your request, in your own words, goes to the template's entry Agent, and a **Working group** card on the matter's board follows the group from then on.
- One template can have several groups at work at once, on different matters. Capabilities lists them under **Templates at work for matters**.
- The main assistant can run one group on other models without changing the template, for example when you ask for a stronger model on one piece of work.
- Groups formed after you save a template use the new version. Changes to a role also reach Agents already at work, from their next turn.

Because the main assistant chooses by the description, write it for that reader: what kind of work the template is for, and what it is not for.

## Build a template

1. In the list (**Graphs**), choose **New Graph**. Give it a **Blueprint ID**, which is the name the main assistant and the template's file use, and a **Description**.
2. Add nodes with **Add node**. Every node is a live Agent and must be bound to a role: select the node and choose its **Agent Preset** in the **Node Inspector**. See [Roles](./roles).
3. In the same inspector, **Custom System Prompt (Append)** adds text after the role's own prompt for this node only, so one role can play different parts in different templates. **Node Plugins** adds whole Plugins to this node alone; Plugins the node already gets from its role or from the whole template keep a badge that says where they come from.
4. Connect two nodes by dragging from one node's output to the other's input, then select the edge and write its handoff text (below).
5. Choose **Apply Changes** in the inspector, then **Save** (Cmd/Ctrl+S).

The pencil next to the template's name edits its ID and description. **Start a task** runs the template once, outside any matter, the way **New Graph** does in Settings › All runs: handy for trying it out.

## What an edge means

Edges are not a fixed pipeline. An edge from A to B is permission: it lets A hand work to B. When A does, A goes to sleep and B wakes with exactly what A sent, the handoff's content and files, and nothing else of A's context. Whether and when to hand off is the Agents' judgement during the run, or yours when you tell them.

- Edges point one way. For B to hand its result back, add an edge from B to A as well.
- Without an edge, A cannot hand work to B. A lead that holds the graph tools can still start any node to work beside it, and a lead with a TaskBoard sends tasks to worker nodes that have no edges at all. The `developer` node of `polished_software_dev` is such a worker. Agents can also add an edge while they run.
- The Agent that hands off sees, in its instructions, each node it may hand to, with that role's description and the edge's text.

That last point is why the edge's text matters. The **Transition description (handoff instruction)** in the **Edge Inspector** is what the sending Agent reads at the moment of handoff, so write it in full: when to hand off, what to pass along, and what the other side should produce. For example: "Once the review passes, hand the full plan, the API contracts and the data model to the developer and ask for runnable code with tests." The more specific it is, the more accurately the two work together.

## Model, validation and saving

The toolbar above the canvas holds the template's default model: a model preset for every node whose role names no model of its own. **Follow default model** leaves those nodes on the global default. See [Models](./models).

**Validate Graph** checks the saved template and shows **Validation passed** or how many errors it found. It looks for a template with no nodes, an edge to a node that is gone, an Agent node without a role, and a template where it cannot tell which node gets the work first. That node is the entry: the one node no edge points into, unless the template's file names its entry point. Validation reads what is saved, so save first. A node whose role no longer exists says so in its inspector.

## Import and export

**Import Graph**, the button next to **New Graph**, turns a team written for another tool into a template of this Space. It reads Oracle's **Agent Spec**, a **Dify DSL** file or a **Microsoft Declarative Workflow**: choose a .yaml, .yml or .json file, or paste its content. The format is told from the content, or pick it under **Format**. Each agent in the file becomes a role, and the way they work together becomes edges.

- **Preview** shows the template, its agents and edges and the **Conversion report** before anything is written. **Import** writes it. **Replace existing** replaces a template or roles with the same names.
- Nothing is dropped silently. The report lists every field that was **Left out** or **Carried over differently**, with where it is in the file.
- Some things never come across. Imported roles use your default model, and the report names the model the file asked for. Tools The One has no match for are listed with the agents that used them. Secrets stay out of the template; the report names them only.
- The One has no engine for fixed steps, so a sequence of steps (an Agent Spec Flow, a Dify workflow, a Declarative Workflow with branches) becomes a lead Agent whose prompt lists the steps in order. The agents those steps call become members, and the lead hands their steps to them.

{/* screenshot pending: ![Importing a Dify DSL file with its conversion report](/docs-assets/images/0.5/en/working-group-templates-import.png) */}

**Export** writes the last saved version as Agent Spec 26.1.2 (YAML or JSON), a Dify DSL file, or a Declarative Workflow that Microsoft's `agent-framework-declarative` Python package runs. Skills, Plugins, model settings and the default model preset stay behind, and the conversion report says so. The file keeps The One's own edges in its metadata, so importing it back unchanged gives you the same template.

In the read-only official Space you can export, but not preview or import.

## Designing a template

The factory teams are built on a few principles. They are worth keeping when you design your own:

- Start with one owner who has the tools the work needs. Add a node only for something the others cannot see or do: other inputs, a narrower context, a different model, or useful parallel work. Copies of one role given the same inputs make the same mistakes.
- Start checkers at the beginning, beside the builder, so what they find arrives before the decisions it should shape.
- Give a checker the request, the data and the interfaces, not the work it checks: a checker that reads the implementation inherits its mistakes.
- Put a rule where it is used, in the handoff it governs or in a Skill (see [Skills and prompts](./skills-and-prompts)), not in a role's standing prompt, where it acts even when it does not apply.
- The lead's path is the cost: every hop on it adds turns. The number of nodes is a result, not a goal.

You do not have to build templates by hand. Ask the main assistant, or use **The Director** bar on the [Atlas](./atlas) canvas. A template, with its roles, is the gene of a working group in [A-Genetic Engineering](../../multi-agent-architecture/a-genetic-engineering); when Agents grow a group further while it runs, by cloning Agents or opening sub-Graphs, that is [Prolifera Engineering](../../multi-agent-architecture/prolifera-engineering).
